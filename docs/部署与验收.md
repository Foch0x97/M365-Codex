# 部署与验收指南

面向自托管者：怎么把 M365-Codex 跑起来，以及怎么确认它真的能用。

> 前置阅读：[README](../README.md) 的合规与风险声明。本项目是非官方逆向实现，
> 使用前请确认你接受其中列出的风险。

---

## 一、部署

### 1. 准备环境变量

```bash
cp .env.example .env
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
```

把生成的 Base64 填进 `M365_CODEX_MASTER_KEY`，再设一个至少 12 位的
`M365_CODEX_ADMIN_PASSWORD`。**没有有效主密钥服务会拒绝启动**——这是刻意的，
避免 Token 以明文入库。

### 2. 启动

```bash
docker compose -f docker/docker-compose.yml up -d
```

或直接跑镜像：

```bash
docker run -d --name m365-codex -p 8080:8080 \
  -e M365_CODEX_MASTER_KEY="$MASTER_KEY" \
  -e M365_CODEX_ADMIN_PASSWORD="$ADMIN_PASSWORD" \
  -v m365-codex-data:/data \
  foch0x97/m365-codex:latest
```

### 3. 验证服务活着

```bash
curl http://127.0.0.1:8080/healthz   # 进程存活
curl http://127.0.0.1:8080/readyz    # 主密钥、数据库迁移、数据目录可写
```

`/readyz` 任一检查不通过返回 503，响应体里会写明是哪一项。

### 4. 进管理台

浏览器打开 **`http://<你的地址>:8080/ui/`**（访问 `/` 会自动跳转过去），
用 `M365_CODEX_ADMIN_PASSWORD` 登录。

管理台与对外 API 的路径是分开的：页面在 `/ui/`，JSON 管理接口在 `/admin/*`，
Codex 用的兼容接口在 `/v1/*`。

### 5. 添加 Microsoft 账号

只有一种方式：管理台的 **PKCE 授权流程**（「添加账号」页）。

1. 点「生成授权链接」
2. 在浏览器打开，用有 Copilot 权限的账号登录
3. 登录后会跳到 Microsoft 的 `nativeclient` 提示页，**复制地址栏的完整 URL**
4. 粘回管理台提交

因为回调落在 Microsoft 自己的页面上，本服务**不需要公网可达**。

### 6. 建 API Key 并配置 Codex

管理台「API Key」页创建，**明文只显示这一次**。然后在「Codex 配置」页复制生成好的
TOML 片段贴进 `~/.codex/config.toml`，把密钥设进环境变量：

```bash
export M365_CODEX_API_KEY=sk-...
```

## 二、验收清单

按顺序做完这些，就能确认部署是好的。

### 基础

| 检查项 | 做法 | 期望 |
|---|---|---|
| 进程存活 | `curl /healthz` | `{"status":"ok"}` |
| 就绪 | `curl /readyz` | `{"status":"ready"}`，各项检查 ok |
| 管理台可进 | 浏览器打开 `/ui/` | 出现登录页，输入密码后进概览 |
| 鉴权生效 | 不带 Key 调 `/v1/models` | 401 |
| 错误密码 | 管理台输错密码 | 401，且连续失败会被节流 |

### 对外 API

| 检查项 | 做法 | 期望 |
|---|---|---|
| 模型列表 | `GET /v1/models`（带 Key） | 返回模型目录 |
| 非流式 | `POST /v1/responses` | 返回完整 Response 对象 |
| 流式 | 同上加 `"stream":true` | SSE 事件流，`sequence_number` 严格递增，以 `response.completed` 收尾 |
| 文件上传 | `POST /v1/files`（multipart） | 201，返回 file id |
| 附件引用 | `input_file` 带上 file id | 文档文本被拼进上下文 |
| 图片输入 | 带 `input_image` | 默认 422 并说明原因（上游能力未校准，不假装支持） |
| Chat 兼容 | `POST /v1/chat/completions` | 返回 `chat.completion` |

### Codex 端到端

配好 `config.toml` 后：

```bash
codex exec "请运行 echo hello 并把输出告诉我"
```

期望看到完整的代理循环：Codex 收到工具调用 → **在你本机执行命令** →
把结果回传 → 得到最终答复。

进一步可验证：多轮对话、读写本机文件、`apply_patch`、Git、MCP、切换
`model` 与 `model_reasoning_effort`（两者都原样透传，不被网关改写）。

> **注意**：Codex 默认会声明 `web_search` 这类 OpenAI 托管工具。本网关执行不了它们，
> 会跳过并在响应头 `x-m365-codex-skipped-tools` 里列出。这不是错误，
> 但意味着那些工具不会生效。

## 三、没有真实账号时怎么验收

仓库里的 `dev/` 提供了一套不依赖 Microsoft 的验收环境，用于验证网关自身
（协议、SSE、工具循环、附件、限额）是否正常：

```bash
# 1. 起一个假上游
node dev/mock-sydney.mjs --port 4300

# 2. 让网关指向它
export UPSTREAM_WS_BASE=ws://127.0.0.1:4300
export UPSTREAM_PATH_TEMPLATE='/chat/{oid}@{tid}'

# 3. 写一个假账号（账号只能经 PKCE 添加，这是有意的安全约束，
#    所以验收环境需要这个脚本绕过交互登录）
M365_CODEX_MASTER_KEY=... node dev/seed-mock-account.mjs --db ./data/m365-codex.sqlite
```

假上游会模拟一个「会调用工具的模型」：声明了工具且请求像是要动手做事时返回工具调用，
收到工具结果后给出引用结果的最终答复。

**这套环境能验证什么**：Responses 协议、SSE 事件、工具代理循环、附件注入、
限额与鉴权、管理台全部功能。
**不能验证什么**：真实 Microsoft 365 Copilot 会不会按我们建模的格式回话——
这部分必须用真实账号实测（见下）。

## 四、排障：403 与 InvalidCopilotLicense

真实环境实测踩过的两个坑，症状都很像"账号没权限"，但成因完全不同。

### 症状一：WebSocket 握手 403，响应体为空

不是账号问题，是**少了 `X-Scenario` 请求头**。

上游对缺失该头的响应是 `Microsoft-HTTPAPI/2.0` 的空 403——没有响应体、没有
`WWW-Authenticate`、没有任何错误说明，看起来和"这个账号被拒绝"一模一样。

实测确认的最小必需组合：

| 项 | 是否必需 |
|---|---|
| `X-Scenario: officeweb` | ✅ **必需**，且取值必须精确（`bizchat` / `M365Chat` / 其它值都是 403） |
| 凭据（`?access_token=` 或 `Authorization: Bearer`） | ✅ 必需，两种放法都行 |
| `X-AnchorMailbox` / `X-SessionId` / `X-Variants` / `Origin` / `User-Agent` | ❌ 都不需要 |
| 路径里的 `/{oid}@{tid}` | ❌ 带不带都能连 |

该头由 `UPSTREAM_SCENARIO` 配置，默认已是正确值；这里记录下来是为了上游变动时能快速定位。

### 症状二：握手成功，但业务层回 InvalidCopilotLicense

这才是真正的账号问题：**没有 Copilot 许可**。见 README 顶部的"账号前提"。

区分两者的方法很简单——看错误出现在哪一层：

- **HTTP 403、连不上** → 协议/请求头问题
- **能连上，`item.result.errorCode` 有值** → 账号或配额问题，上游会把原因写在 `message` 里

### 症状三：网页端提示"Copilot Chat 在你所在的区域不可用"

区域限制跟随**租户注册地**，不是你的出口 IP——实测从东京出口访问，租户
`tenant_region_scope=AS` 的账号照样被拒。**换代理节点没有用**，只能换租户。

## 五、仍需真实账号确认的事项

以下内容依赖真实上游，**部署方需自行验证**，本项目的自动化测试无法覆盖：

> **已经校准过的部分不在此列**。2026-07-27 用真实账号跑通了握手与请求/响应格式：
> 请求侧 `arguments[0]` 里是**单数 `message` 对象**（早期按公开资料建模的
> `messages[]` 数组形态已被证伪，从未在真实上游跑通），响应侧业务负载在 **`item`**
> 字段里（`item.messages[]` / `item.result`），不是 `arguments[0]`。
> 这部分现在以实测为准，见 `adapter/codecV1.ts`。

下面这些**仍未验证**，因为校准所用账号没有 Copilot 许可，上游在协议完全正确之后
才于业务层拒绝（`InvalidCopilotLicense`），拿不到真实的生成内容：
- **上游是否原生支持结构化工具调用**。默认 `TOOLS_MODE=auto` 同时下发结构化声明与
  提示词约束、两种回应都解析；确认真实能力后可收敛为 `native` 或 `prompt`。
- **图片输入**是否可用（`UPSTREAM_IMAGE_INPUT`，默认关闭）。
- 真实的**限流阈值与错误码分布**，据此调整冷却与重试参数。
- 精确 token 用量、思考等级是否真正分级、引用来源区间——这些在上游不提供时
  如实留空，不编造。
